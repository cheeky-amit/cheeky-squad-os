# cheeky-squad-os dual-platform audit

Date: 2026-08-08
Mode: read-mostly project audit
Status: complete with concerns

## Executive verdict

`cheeky-squad-os` is a mature Claude Code plugin with an unusually strong discipline model and a good automated test base. It is not yet a dual-platform product.

The central product problem is slightly different from "generated agents are user-wide":

- The generated Claude role files are already project-local at `.claude/agents/<role>.md`.
- The generated squad is not self-contained. Its role files, state, dispatch, verification, permission behavior, and lifecycle still depend on the installed `cheeky-squad-os` plugin and `${CLAUDE_PLUGIN_ROOT}`.
- The output is therefore an instance of the base plugin, not a standalone project or independently installable plugin.

The right move is not a second implementation or a rename pass. Keep one provider-neutral squad contract, then compile it into Claude and Codex adapters. Add two explicit export targets:

1. **Project export:** a self-contained squad committed into one repository, with no user-level writes and no dependency on a globally installed Squad OS plugin after export.
2. **Plugin export:** a new independently versioned package with Claude and Codex manifests, shared skills/scripts, and provider-specific role adapters.

## What is already excellent

### 1. The product has a real point of view

"Ship the discipline, not the team" is more than positioning. The code and docs consistently implement goal binding, generated roles, explicit ownership, hand-offs, verification, sourced beliefs, declared intent, stop conditions, and human rulings.

### 2. The repository distinguishes mechanisms from instructions

The architecture explicitly separates hook/parser-enforced behavior from behavior merely requested in prompts. That honesty is rare and should remain a release gate for every provider adapter.

### 3. Security-sensitive paths have regression coverage

The permission hook tests path normalization, traversal, broad scopes, `.squad/` reservation, another role's state, Bash scaffolding, plan gating, worktree root resolution, and belief ownership. This is the strongest part of the implementation.

### 4. The current Claude implementation is not the thing to replace

The Claude path already works. The existing 238 tests are a compatibility suite that a portability refactor must preserve. Build around it with adapters instead of forcing shared lowest-common-denominator behavior into the current files.

## Critical findings

### P0. A generated squad is not an independent artifact

Evidence:

- `squad-role` writes `.claude/agents/<name>.md` and `.squad/role-goal-<name>.md`.
- Dispatch and provisioning call scripts through `${CLAUDE_PLUGIN_ROOT}`.
- Permission behavior comes from hooks registered by the base plugin manifest.
- Generated role bodies refer back to plugin skills, templates, commands, and Claude-specific runtime behavior.

Impact:

- Copying `.squad/` and `.claude/agents/` to another repository does not reproduce the system.
- Removing or disabling the base plugin removes orchestration and guardrail behavior.
- A generated squad cannot be versioned, shared, installed, or released independently.

Required change:

Add a `squad-export` capability with `project` and `plugin` targets. An export must include every runtime file it needs or reference only files native to the target project/package.

Acceptance test:

> In a fresh temporary HOME with the base Squad OS plugin absent, export a two-role squad, start Claude or Codex in the target, discover the local squad, dispatch the read-only roles, collect their hand-offs, and run verification. No file outside the target is changed.

### P0. Core state mixes provider-neutral intent with Claude runtime configuration

The roster currently stores Claude tool names and models directly:

- `Read`, `Write`, `Edit`, `Bash`, `Glob`, `Grep`
- `sonnet`, `opus`, `haiku`, `fable`, `inherit`
- `.claude/agents/...`
- Claude MCP naming examples
- Claude worktree and Agent Teams semantics

Codex custom project agents use TOML files under `.codex/agents/`, require `name`, `description`, and `developer_instructions`, use OpenAI model identifiers and `model_reasoning_effort`, and inherit Codex sandbox/permission configuration.

Required change:

Create a provider-neutral schema, for example:

```json
{
  "schema_version": 2,
  "role": {
    "id": "report-writer",
    "purpose": "Write the verified final report",
    "capabilities": ["read_files", "write_owned_files", "run_local_checks"],
    "write_scope": ["reports/**"],
    "reasoning_profile": "balanced",
    "isolation_profile": "project-write",
    "stop_conditions": []
  },
  "providers": {
    "claude": {},
    "codex": {}
  }
}
```

Provider adapters then map capabilities, model profiles, agent paths, frontmatter/TOML, tool names, and permission semantics. Provider overrides remain possible, but Claude vocabulary no longer defines the core contract.

### P0. The current permission hook is not a Codex enforcement mechanism

The output decision shape is compatible, and Codex supplies `agent_type`. The important mismatch is file editing:

- Claude sends `Edit`/`Write` with `tool_input.file_path`.
- Codex reports file edits as canonical `apply_patch`, with the patch in `tool_input.command`.
- Codex `PermissionRequest` runs only when Codex is already about to ask for approval. Normal in-workspace edits may not reach this event.

Therefore the existing hook cannot be reused as proof of Codex file-scope enforcement. Adding `apply_patch` to a matcher is insufficient.

Required change:

- Keep the existing Claude PermissionRequest hook behavior and tests.
- Build Codex-specific hook fixtures for `apply_patch`, Bash, subagents, and project hooks.
- Decide explicitly whether Codex out-of-scope writes are hard-blocked in `PreToolUse`, limited by a role-specific permission profile, or merely instructional.
- Until exact enforcement is proven, run Codex write roles sequentially and label `file_scope` as an ownership contract, not a mechanical sandbox.

Do not publish a shared "mechanically enforced on both" claim until an end-to-end Codex test proves it under the relevant permission modes.

### P0. There is no Codex package or project surface

Missing:

- `.codex-plugin/plugin.json`
- project agents under `.codex/agents/*.toml`
- repo-local skills under `.agents/skills/` for a self-contained project export
- root `AGENTS.md`
- Codex hooks configuration/manifest
- Codex installation and invocation docs
- Codex fixtures or smoke tests

The current Codex plugin system can reuse much of this repository:

- A native plugin uses `.codex-plugin/plugin.json`.
- Plugins can bundle skills and lifecycle hooks.
- Codex sets `PLUGIN_ROOT` and also compatibility variables including `CLAUDE_PLUGIN_ROOT`.
- Repo-local skills can live under `.agents/skills`.
- Codex can import Claude Code instructions, skills, plugins, hooks, slash commands, and subagents via `/import`.

The import flow is a useful migration shortcut, but it is not a substitute for a native, testable Codex adapter.

### P0. Plugin export and project export are currently conflated

They solve different jobs:

| Output | Best for | Must contain |
| --- | --- | --- |
| Project export | One squad attached to one repository | local instructions, provider agent files, local skills/runtime, state schema, hooks/config, tests |
| Plugin export | Sharing/installing a squad across projects or people | dual manifests, skills, hooks, packaged role definitions, activation/dispatch workflow, version/license/docs |

Make the choice explicit during export. Never write to `~/.claude`, `~/.codex`, or `$HOME/.agents` unless the user explicitly selects user scope.

## High-priority findings

### P1. Add dual manifests, but do not duplicate the implementation

Keep the existing `.claude-plugin/plugin.json`. Add `.codex-plugin/plugin.json` pointing to the same shared `skills/` and a Codex-compatible hook definition.

Use one source for hook registration if both hosts can consume it safely; otherwise generate both manifests from one canonical metadata file and assert equality for name/version/description in CI.

### P1. Codex roles need a real adapter

For a project export, generate one `.codex/agents/<role>.toml` per active role with `name`, `description`, `developer_instructions`, optional `model`, optional `model_reasoning_effort`, and a conservative sandbox/permission profile.

For a plugin export, do not assume Codex discovers custom agents directly from the plugin bundle. Current native plugin packaging documents skills, hooks, MCP servers, and assets, while project custom agents live under `.codex/agents/`.

Use one of these explicit designs:

1. A plugin activation skill materializes project-local `.codex/agents/*.toml` after the user confirms the target project; or
2. A dispatch skill loads packaged provider-neutral role definitions and spawns Codex subagents with the full role prompt baked into each task.

The second design is more portable. The first offers better local discoverability and per-agent configuration. Supporting both is reasonable after the schema/compiler exists.

### P1. The repository itself needs cross-agent contributor guidance

Add a concise root `AGENTS.md` containing the architecture map, sources of truth, quality gates, generated-file rules, provider adapter boundaries, security invariants, and documentation expectations.

Add a small `CLAUDE.md` only for Claude-specific contributor routing and a pointer to `AGENTS.md`. Do not maintain two copies of the same global rules.

### P1. Replace duplicated prose schemas with machine-readable contracts

The roster schema, role-goal schema, role-plan schema, placeholders, model enums, and hook behavior are repeated across templates, skills, examples, docs, and CI shell snippets.

Add versioned schemas and deterministic compilers:

- `schemas/squad.schema.json`
- `schemas/roster.schema.json`
- `schemas/role.schema.json`
- `scripts/compile-claude.*`
- `scripts/compile-codex.*`
- golden fixtures under `tests/fixtures/`

Generate or validate examples from those sources. Avoid adding more inlined copies as Codex support lands.

### P1. Add a compatibility matrix and honest degradation policy

Document each capability as `native`, `adapted`, `instructional`, or `unsupported` per host:

| Capability | Claude | Codex target |
| --- | --- | --- |
| Goal injection | Native SessionStart + prompt baking | Native SessionStart/SubagentStart + prompt baking |
| Generated local roles | `.claude/agents/*.md` | `.codex/agents/*.toml` |
| Multi-agent dispatch | Subagents / Agent Teams / Workflow | Codex multi-agent collaboration |
| File ownership | PermissionRequest guard | Must be re-proven; default to sequential writes until then |
| Worktree isolation | Claude role/worktree path | Separate adapter; do not imply parity |
| Evergreen scheduling | Claude-specific options | Codex automation/scheduled-task adapter |
| Verification and belief ledger | Shared scripts/state | Shared scripts/state |

This table should be tested documentation, not marketing copy.

### P1. Simplify the public story

The repository has 8,984 lines of Markdown, including three very large examples and two long architecture explanations. The depth is valuable, but the first-run path is expensive to understand.

Recommended layers:

1. README: problem, 90-second demo, install for Claude/Codex, project vs plugin export, compatibility matrix.
2. `docs/concepts/`: goal, role, hand-off, verification, world, partner.
3. `docs/providers/claude.md` and `docs/providers/codex.md`.
4. `docs/security.md`: only mechanical guarantees and known gaps.
5. `docs/architecture/`: compiler/IR/adapters and ADRs.
6. Examples generated from fixtures, not hand-maintained copies.

## Medium-priority findings

### P2. Versioning is manually duplicated

Plugin and marketplace versions currently agree at `1.0.0`, but every skill still declares `version: 0.1.0`. These may be intentionally independent, yet they read as stale and there was already a historical marketplace-version drift fix.

Choose and document one policy: lock all shipped component versions to the release version, or keep component versions independent and test/document that policy. Add a release check for every intended equality.

### P2. CI covers one OS and no provider adapters

Add Ubuntu and macOS jobs, Claude and Codex fixture validation, TOML parsing, JSON Schema validation, golden-output diffs, a fresh-HOME self-contained export smoke test, and a no-user-scope-write assertion.

### P2. CI bootstrap should verify downloaded tooling

CI pins ShellCheck by version but downloads and extracts a release archive without checking a checksum. Add a verified digest or use a trusted action/package path with its own pinning policy.

### P2. Add open-source governance artifacts

Consider `SECURITY.md`, issue/PR templates, a support and compatibility policy, an ADR directory, and a Code of Conduct if broader community contribution is a goal.

                                  |
                                  v
                     provider-neutral squad schema
                    (.squad/squad.json + role specs)
                                  |
                  +---------------+---------------+
                  |                               |
                  v                               v
          Claude adapter/compiler          Codex adapter/compiler
          .claude/agents/*.md              .codex/agents/*.toml

          Agent Teams/Workflow             Codex multi-agent collaboration
                  |                               |
                  +---------------+---------------+
                                  |

The shared runtime owns semantics. Adapters own syntax and host behavior.

## Execution roadmap

### Phase 0: lock the product decision

Decision: generated squads are independent artifacts. Default export scope is project-local. User-wide installation is opt-in only.

Deliverables: ADRs for the portable schema/adapters and Codex enforcement policy, plus the compatibility matrix.

Exit gate: maintainers can explain which files are canonical, which are compiled, and what survives without the base plugin.

### Phase 1: native Codex base-plugin compatibility

Deliverables: `.codex-plugin/plugin.json`, Codex hook definitions and fixtures, root `AGENTS.md`, provider docs, native installation, and `/import` bridge instructions.

Exit gate: the base plugin installs from a local Codex marketplace and exposes skills in a fresh session; context hooks are verified; permission behavior is labeled at its proven level.

### Phase 2: provider-neutral role schema and compilers

Deliverables: schema v2 and migration, Claude compiler preserving current output, Codex compiler emitting project-agent TOML, model/capability mapping, and golden fixtures.

Exit gate: one canonical role produces valid Claude and Codex agents; all 238 current tests and new adapter/schema tests pass.

### Phase 3: self-contained exports

Deliverables: `squad-export project`, `squad-export plugin`, no-global-write default, local runtime/skills/hooks, and generated manifest/license/docs/version files.

Exit gate: a fresh-HOME project export works without the base plugin, and a fresh local-marketplace plugin export installs independently.

### Phase 4: parity hardening and release

Deliverables: two-role smoke tests for both hosts, safe Codex write coordination, CI matrix, release automation, security/support policies, and a dual-platform README relaunch.

Exit gate: every compatibility-table row links to a test or is visibly marked instructional/unsupported.

## What not to do

- Do not fork the entire codebase into `claude/` and `codex/` copies.
- Do not replace `.claude` strings with a generic variable and call that portability.
- Do not store Claude and Codex model IDs in one untyped `model` field.
- Do not claim the current PermissionRequest hook enforces Codex writes.
- Do not make user-wide installation the default for generated squads.
- Do not rely on Codex `/import` as the permanent architecture.
- Do not publish a generated plugin that still requires the generator plugin at runtime.
